# MCP Server

Last updated: 2026-11-12

`brewpage-mcp` 1.19.0 provides thirty tools to publish and manage HTML, Markdown, JSON, KV, files, and multi-file sites, and to read what visitors save on a page, from compatible MCP clients. It runs locally over stdio (Node.js 20 or newer) or remotely without install, and calls the BrewPage API.

## Installation

### Remote (no install)

One remote MCP server for every client: `https://brewpage.app/mcp` (Streamable HTTP, no authentication, same 30 tools). Add it by URL in Claude (a custom connector), ChatGPT (a custom MCP server) or any Streamable HTTP client.

Claude Code: `claude mcp add --transport http brewpage --scope user https://brewpage.app/mcp` (leave out `--scope user` to add it to the current project only), or in `.mcp.json`:

```json
{
  "mcpServers": {
    "brewpage": {
      "type": "http",
      "url": "https://brewpage.app/mcp"
    }
  }
}
```

### Claude.ai and Claude Desktop

Claude calls a remote MCP server a custom connector. Add it once in Claude on the web; Claude Desktop picks it up too. Nothing to install.

1. Open **Customize** > **Connectors**.
2. Click **+ Add**, then **Add custom connector**.
3. Name it **BrewPage**, paste `https://brewpage.app/mcp` and click **Continue**.
4. Click **Continue** again, choose **No sign in** under Authentication and click **Add**.

The free plan includes one custom connector.

Local fallback (stdio, needs Node.js; the same tools): add to Claude Desktop's `claude_desktop_config.json`:

```json
{
  "mcpServers": {
    "brewpage": {
      "command": "npx",
      "args": ["-y", "brewpage-mcp@1.19.0"]
    }
  }
}
```

### Claude Code

The remote command above is the default. Local fallback: register a project-scoped stdio server:

```bash
claude mcp add --transport stdio --scope project brewpage -- npx -y brewpage-mcp@1.19.0
```

This writes `.mcp.json` in the project root; user-scoped registration uses `--scope user`. See the [official Claude Code MCP guide](https://code.claude.com/docs/en/mcp).

### One-liner

```bash
npx -y brewpage-mcp@1.19.0
```

This starts a stdio server for an MCP client, not an interactive publishing shell. Other clients can use the same `npx` command and pinned arguments.

## Available Tools

| Tool | Description |
|------|-------------|
| `publish_html` | Publish HTML, Markdown, code or JSON with optional filename and toolbar |
| `update_html` | Replace HTML/Markdown or code content with the owner token; omitted format preserves the stored format, except a whole HTML document makes a Markdown page an HTML page; optional `tags` replace the stored ones |
| `get_page` | Fetch raw HTML page content; optional password |
| `publish_file` | Fetch a file from a URL and upload it; HTML and Markdown become pages; optional filename |
| `publish_site` | Publish `entryContent` or a `files` bundle; optional entry path |
| `republish_site` | Replace the complete site bundle at the same ID/link; absent files are removed |
| `publish_json` | Publish a JSON object, array, or JSON-encoded string |
| `get_json` | Fetch a JSON document; optional password |
| `update_json` | Replace a JSON document with the owner token |
| `publish_kv` | Create a KV store with an initial key/value |
| `set_kv` | Set or replace a key in an owned KV store |
| `get_kv` | Fetch a key's value; optional password |
| `update_hosting` | Change eligible publication delivery mode using owner authority and hosting version |
| `delete_resource` | Delete a resource (incl. sites) by namespace/id with owner token |
| `set_visibility` | Hide or show a public publication in the gallery and sitemap; link unchanged |
| `set_title` | Rename an HTML page or site; the title stays on republish; link unchanged |
| `bind_token` | Add an owner token to your profile with an admin token |
| `mint_token` | Mint a profile token with an admin token; shown once |
| `set_domain` | Connect a domain you own to an HTML page or site; returns the DNS records to create |
| `list_domains` | List the profile's custom domains with status and DNS records (admin token) |
| `check_domain` | Check a custom domain's DNS now; status `pending_dns` -> `verifying` -> `active` |
| `remove_domain` | Remove a custom domain and free its slot; the BrewPage link keeps working |
| `get_guide` | Read the short Page data guide before writing a page that saves what visitors enter |
| `get_page_data` | Read what visitors saved on your page: the settings and usage, or one list's entries |
| `set_page_data` | Write author entries (for example today's menu) without republishing the page |
| `configure_page_data` | Change who can read a list and its limits; only what you name changes |
| `delete_page_data` | Delete entries by id, or every entry in a time range |
| `search_gallery` | Browse public content or list owned resources with `mine` and `ownerToken` |
| `get_stats` | Get platform-wide usage statistics |
| `get_limits` | Get the current upload limits (`GET /api/limits`) |

## Custom Domains

A page or site can also live on a domain you own, such as `www.example.com` or `example.com`: free, 5 per profile, for HTML pages of format `html` and for sites without a password. The owner token must be in a free BrewPage profile (sign in at https://account.brewpage.app).

```
set_domain(type="html", namespace="public", id="aBcDeFgHiJ", hostname="www.example.com")
check_domain(type="html", namespace="public", id="aBcDeFgHiJ")
```

`set_domain` prints the DNS records to create at your DNS provider, exactly as returned: a TXT record at `_brewpage.<host>` plus a CNAME to `domains.brewpage.app`; a root domain takes the A record shown, or ALIAS. After you create them, `check_domain` reports `pending_dns`, then `verifying`, then `active`; HTTPS is issued automatically and the BrewPage link keeps working. `list_domains` (admin token) shows all domains of the profile, `remove_domain` frees a slot. `publish_html` and `publish_site` take an optional `domain` to connect it while publishing.

## Page Data

A published HTML page or site can save what its visitors enter: form answers, a guestbook, votes, scores, game progress. No keys and no backend of your own. The page loads the script `https://brewpage.app/js/state.js` and is published with a `state` argument that names its lists; `{}` is enough to start.

```
get_guide(topic="page-data")
publish_html(content="<!doctype html>...", state={"collections": {"guestbook": {"mode": "shared"}}})
get_page_data(namespace="priv-abc123", id="aBcDeFgHiJ", collection="guestbook")
```

By default each visitor reads and writes only their own entries (`private`). A `shared` list is readable by everyone; with `write: "author"` only you write it, for example a menu. You, the author, read everything: in the Data tab behind the management link, or with `get_page_data`.

`get_guide` returns the short reference the assistant reads before writing such a page. `publish_html` and `publish_site` take `state` on create and the page gets its own address `https://<label>.brewpage.app`; `update_html` and `republish_site` take it on update, where lists named in the call are added or updated and the others stay. `set_page_data` writes author entries without republishing, `configure_page_data` changes who can read a list and its limits, `delete_page_data` removes entries by id or by time range.

After publishing, the assistant gives you the page link and the management link, keeps the owner token and shows it on request; neither is ever posted publicly. The four page-data tools take `namespace`, `id` and `ownerToken`, or the management link alone as `manageUrl`, which works in a later chat when the token is not at hand.

## Visibility and Delivery

All five publish tools accept optional `deliveryMode: "path" | "subdomain"`; it is sent as `X-Delivery-Mode`, without changing content bodies. Omitted namespace is private (a generated `priv-<random>` namespace): unlisted and not indexed; anyone with the link can still open it. `public` lists HTML, sites and files in the gallery and sitemap, so Google, Bing and AI search can find and index them; public pages are served on the brewpage.app domain for the strongest reach (a site always gets its own subdomain). Never put secrets in a public publication. Password-protected publications, JSON and KV are never listed.

These tools wrap a subset of the backend-generated public REST contract. MCP TTL inputs take days or a string such as `2w` (default 15); the server rounds to whole days and clamps to 1–30 (up to 90 with a profile token), and owner-specific caps and eligible automatic extensions can affect actual expiry. Use returned `expiresAt`. Tolerated-input adjustments come back in the response `notices` array, printed as `Notice (code): message`; `secret-detected` prints as `WARNING (code): message`; a live BrewPage token or manage link in public content prints first as `SECURITY ALERT (credential-published): …` (remove it and reset it). A minted `manageUrl` prints as `MANAGE LINK (private): …`: give it to the user privately, never publish it. Set `BREWPAGE_OWNER_TOKEN` (local server only) for a default owner token; outputs name it instead of printing it. Secrets allowed; likely ones are flagged in notices. For a secret: private namespace + password. `get_page` reads stored rendered HTML or format-specific code/text, rather than owner-only original source or a browser viewer.

For a fresh publication, sites and HTML pages of format `HTML` outside `public` (including the generated unlisted namespace) always use **Dedicated subdomain**; omit `deliveryMode` there. An explicit `path` there is not rejected: the publication is created on its subdomain and the result reports `deliveryModeMatched: false`, `deliveryModeReason: "policy:subdomain-required"` and a `Delivery notice:` line. Everything else in any namespace (Markdown, code/text, files, JSON, KV, public HTML) defaults to **Promotion** (`path`) and may choose **Dedicated subdomain** (`subdomain`), including when password-protected. Markdown raw HTML is rendered through an allowlist (no scripts, styles, event handlers, forms or embeds; links `http`/`https`/`mailto`/`tel`/relative); earlier pages change only when republished. Promotion has stricter active-document restrictions. Each NEW site gets one publication-specific host for its complete bundle, preserving relative/root-relative paths; missing assets return 404 with no SPA fallback. Third-party widgets may need provider configuration.

Use the server's primary `link` exactly, including the root slash. Never reconstruct a host from namespace or ID. Responses expose `routingCohort`, `deliveryMode`, `requestedDeliveryMode`, `effectiveDeliveryMode`, `deliveryModeMatched`, `modeLocked`, `hostingVersion`, `access`, and the trusted-apex `managementLink` when supplied. NEW password links are clean URLs: do not append `?p=`; browser readers unlock through the trusted gateway. API calls and owner tokens stay on the configured apex API origin.

When `deliveryMode` is omitted for a `public` HTML or Markdown page, the server may publish it on its own subdomain if the page needs browser features a BrewPage link does not provide. `publish_html` then prints `deliveryModeReason: "auto:<codes>"` and a `Delivery notice:` line; pass `deliveryMode: "path"` to keep a BrewPage link, or change it later with `update_hosting`. `advisory:<codes>` (from `publish_html` or `update_html`) means the address was not changed but such features were found. Neither line appears when nothing applies.

When creation returns an existing publication, it keeps its actual link, cohort, and mode even when another mode was requested. OLD publications show **Existing link** with null mode metadata and retain their legacy links and behavior. Content updates and site republishing preserve hosting.

## Publish and Update

Ask your assistant to publish the content, save the returned owner token, and share the returned primary link. `publish_html`, `publish_site`, `publish_json`, and `publish_kv` accept `password` and `ttlDays` (days or a string such as `2w`; default 15; clamped to 1–30, up to 90 with a profile token). `publish_file` accepts a source `url`, optional `namespace`, `filename`, and `deliveryMode`; it does not expose base64, password, or TTL inputs.

```text
publish_html(content="<h1>Report</h1>", format="HTML", ttlDays=15)
publish_site(files=[{"path":"index.html","content":"<link rel='stylesheet' href='/style.css'><h1>Site</h1>"},{"path":"style.css","content":"body{font-family:sans-serif}"}])
```

For sites, provide exactly one of `entryContent` or a non-empty `files` array of `{path, content}`. `entry` defaults to `index.html`. `republish_site` requires `namespace`, `id`, and `ownerToken`; it replaces the full file set, removing files absent from the new bundle. It also accepts `entry`, `ttlDays`, and `tags` (replace the stored tags, `[]` clears, omitted keeps them); its TTL input is ignored (existing expiry is kept; a `ttl-ignored` notice is returned).

Call `get_limits` before publishing a large or multi-file site. A request is at most 25 MiB; a site at most 200 files, 5 MiB per file and 20 MiB in total; each path at most 380 characters. System files such as `.DS_Store` and `__MACOSX/` are skipped and never count; files with an unsupported extension or a too-long path are skipped and reported in notices. Without `entry`, the root `index.html` is the entry, else the shallowest HTML file. A site limit hit answers 400 with a message naming the limit, as does a PDF/Office file that is unreadable or password-protected; 413 means the request is over 25 MiB, has too many files and form fields, or a file name/path is too long; 422 means no servable file is left; 503 means busy: retry after `Retry-After` seconds (failed publish tools print it).

### Change Hosting

`update_hosting` changes an eligible NEW publication (not a site, not a non-public `html`-format HTML page) between Promotion and Dedicated subdomain. Required inputs: `type` (`html`, `file`, `json`, or `kv`), `namespace`, `id`, `ownerToken`, and `deliveryMode`; `expectedVersion` (current `hostingVersion`, integer ≥1) is optional, pass it when known.

It calls owner-only `PATCH /api/{html|files|json|kv}/{namespace}/{id}/hosting` with `{deliveryMode}` plus `expectedVersion` when given, and `X-Owner-Token`. Mismatches are reported, not rejected: a stale or omitted version still applies the choice (a stale one adds `deliveryModeReason: "policy:version-stale"`); sites and non-public `html`-format HTML pages stay on their subdomain (`policy:mode-locked`) and OLD links stay unchanged (`policy:classic-link`), each answered 200 with `deliveryModeMatched: false` and a `Delivery notice:` line. Wrong owner returns 403, a malformed version (not a positive integer) 400, and a paused real change 503. Selecting the current mode returns 200 without incrementing the version. Always use the returned primary link; the reserved publication host survives both directions.

```text
update_hosting(type="html", namespace="public", id="aBcDeFgHiJ", ownerToken="tok_...", deliveryMode="subdomain", expectedVersion=1)
```

### Delete a Resource

`delete_resource` takes `namespace`, `id`, `type` (`html`, `site`, `kv`, `json` or `file`) and `ownerToken` (default `BREWPAGE_OWNER_TOKEN`, local server only); path segments are URL-encoded.

## Owner Token Reminder

Every publish response includes your **owner token**. You need it to update or delete your content later. Save it somewhere safe — it cannot be recovered if lost.

Optional: sign in free (Google or any email) at https://account.brewpage.app to never lose your pages or tokens and to mint tokens that never expire. Not needed to publish.

Pass it to owner-only tools and to `search_gallery(mine=true, ownerToken="tok_...")` to list your resources. The `publish_site`, `publish_json`, and `publish_kv` tools accept an existing `ownerToken` to group new content under the same owner.

## Configuration

`BREWPAGE_URL` defaults to `https://brewpage.app`. Set it to an authorized BrewPage apex API origin, never a publication host.
