## OpenAPI Specification

Download the public OpenAPI 3.1 snapshot. Backend generation owns schema authority; the YAML representation is derived, and the Scalar JSON copy is identical. Export provenance is committed alongside the snapshot.

| Format | Source |
|--------|--------|
| **YAML** | [openapi.yaml](https://github.com/kochetkov-ma/brewpage-openapi/blob/main/openapi/openapi.yaml) |
| **JSON** | [openapi.json](https://github.com/kochetkov-ma/brewpage-openapi/blob/main/openapi/openapi.json) |
| **Live endpoint** | [brewpage.app/v3/api-docs](https://brewpage.app/v3/api-docs) |

HTML API reads return stored rendered HTML, or raw code/text with format-specific MIME. The owner-only `/api/html/{ns}/{id}/source` endpoint returns original authored source; `/settings` returns publication settings. Browser share links may provide a viewer. JSON reads return the stored JSON value, including objects, arrays, scalars or null; do not assume a metadata envelope. File reads return bytes and accept `dl` to request attachment delivery.

## Authentication

Unprotected publication reads need no credential, including unlisted content whose link is known. Password-protected reads require access; owner listing and mutations require owner authority. Admin endpoints require separate administrative authentication.

Owner mutations use the original token returned at creation:

| Method | Example |
|--------|---------|
| Header | `X-Owner-Token: tok_xxx` |

Programmatic protected reads:

| Method | Example |
|--------|---------|
| Header | `X-Password: secret` |

NEW protected browser links use the clean returned `link` and a trusted top-level unlock gateway. Never append passwords or owner tokens to NEW share URLs. OLD publications retain historical access behavior, including legacy query-password parsing where supported; this is not the NEW browser unlock mechanism. API and owner operations remain on the apex, not content hosts.

## Publication Delivery

REST creation defaults to `ns=public`; the MCP wrapper defaults to an unlisted generated namespace. Only unpassworded `public` content is eligible for gallery/search discovery. Unlisted, protected or otherwise ineligible native responses carry `noindex`; eligible public HTML, sites and files may permit indexing.

For fresh NEW publications, sites (any namespace) and HTML pages of format `html` outside `public` always use **Dedicated subdomain**; send no `X-Delivery-Mode` there. Mismatches are reported, not rejected: an explicit `path` creates the publication on its subdomain with `deliveryModeMatched: false` and `deliveryModeReason: "policy:subdomain-required"`, and a content update that turns a non-public `path` page into format `html` moves it to its subdomain (the returned `link`; the old path redirects there). `X-Delivery-Mode` sent with a content update or site republish is ignored and reported as `policy:republish-keeps-mode`. Each of these responses carries a human-readable `deliveryNotice`. Everything else in any namespace (Markdown, code/text, files, JSON, KV, public HTML) defaults to **Promotion** (`path`) and may select **Dedicated subdomain** with `X-Delivery-Mode: subdomain`. Existing publications keep their mode. Every NEW site bundle has a publication-specific host with relative/root-relative paths and native missing-file 404 responses, without an SPA fallback. Promotion has stricter active-document restrictions.

Keep the returned primary `link` exactly, including root slashes; do not reconstruct a host from namespace or ID. Responses expose cohort, actual/requested/effective modes, `deliveryModeMatched`, `modeLocked`, `hostingVersion`, `access`, an apex `managementLink`, and optional `deliveryModeReason`/`deliveryNotice` (omitted when nothing applies). When creation returns an existing publication, it retains its own cohort, link, and mode. OLD links remain compatible and show **Existing link**, with missing or null effective-mode metadata.

`POST /api/html` and `PUT /api/html/{ns}/{id}` responses may also include two optional strings. When a public HTML or Markdown page is created without `X-Delivery-Mode` and its inline code relies on browser features a BrewPage (`path`) link does not provide, the server publishes it on its own subdomain and returns `deliveryModeReason: "auto:<codes>"`; `requestedDeliveryMode` stays null. `advisory:<codes>` means the address was not changed (explicit `path`, a content update, or an existing page returned for an identical repost) but such features were found. `deliveryNotice` is a human-readable sentence explaining the reason. Codes are comma-separated in a fixed order, drawn from `storage`, `cookies`, `history`, `downloads`, `top-navigation`, `media-capture`, `pointer-lock`, `embeds`, `fullscreen`. Both fields are omitted when nothing applies; send `X-Delivery-Mode: path` to keep a BrewPage link.

Markdown pages render raw HTML through an allowlist: formatting, images, video/audio, `details`/`summary` and tables stay; scripts, styles, event handlers, forms, frames/embeds and `meta`/`base`/`link` are removed; links allow `http`, `https`, `mailto`, `tel`, relative and `#anchor` URLs, images also `data:`. A lone unknown tag such as `<author>` shows as text. Pages published earlier change only when republished.

An eligible NEW publication can change hosting through owner-only `PATCH .../hosting` with `{"deliveryMode":"subdomain","expectedVersion":1}`; send the current `hostingVersion` when known, `expectedVersion` is optional. The route also accepts sites. Mismatches are reported, not rejected: a stale or omitted version still applies the choice (a stale one adds `deliveryModeReason: "policy:version-stale"`); sites and non-public `html`-format HTML pages stay on their subdomain (`policy:mode-locked`) and OLD links stay unchanged (`policy:classic-link`), each answered 200 with `deliveryModeMatched: false` and a `deliveryNotice`. Wrong owner returns 403, a malformed version (not a positive integer) 400, and a paused real change 503. Current-mode no-op preserves the version; ordinary content updates and site republishing preserve hosting. The reserved publication host survives both switch directions.

Owners can revoke reader access for a NEW protected publication through `POST .../access/revoke` with `X-Owner-Token` and no body. Readers must unlock again; other publications and offline copies are unaffected.

## Rate Limits

Limits depend on operation and visibility. Handle the running API's 429 responses and any `Retry-After` header rather than assuming a single upload quota.

## Size Limits

| Resource | Max Size | Max Count |
|----------|----------|-----------|
| HTML page | 5 MB | — |
| KV value | 1 MB | 1,000 keys/store |
| JSON doc | 1 MB | 10,000 docs/namespace |
| File | 5 MB | 1,000 files/ns |
| Site | 20 MB total, 5 MB/file | 100 files/site |
| TTL | 1–30 days (default 15) | — |

These are repository defaults (MiB); video uploads allow up to 20 MiB and audio up to 5 MiB. KV key counts apply per store; JSON and file counts apply per namespace. The running deployment may apply different limits or owner-specific TTL caps. Eligible content may receive automatic TTL extensions; returned `expiresAt` describes the current expiry.
